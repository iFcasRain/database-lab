# 应用测试报告（第 7—9 周）

## 1. 测试目标

验证 v1.0 应用在真实 SQL Server 数据库上是否满足以下要求：

1. 登录、未登录、越权访问都能被正确拦截，且提示友好；
2. 参数错误、约束冲突、库存不足等异常能被统一处理，事务能正确回滚；
3. 下单、订单明细写入、库存扣减、积分结算形成完整闭环；
4. 参数化查询能抵御 SQL 注入尝试；
5. 测试结束后正式样例数据不被破坏。

## 3. 测试方法

1. **真实数据库，不用替身**：测试直接连接迁移后的 `ConvenienceStoreDB`，走完整的分层调用链（页面层 → 业务层 → 数据访问层 → 数据库），因此数据库权限、事务、约束冲突都被真实验证；

## 5. 重点验证说明

### 5.1 事务回滚真的发生了吗

T22 的流程是：店员提交 900 件饮用水（库存只有 24）。业务层在事务中读取库存、发现不足后抛出 `BusinessRuleError`，`transaction()` 捕获异常并执行 `IF @@TRANCOUNT > 0 ROLLBACK TRANSACTION`，因此订单、明细一条都不会留下，库存保持原值。断言不仅检查了 409 状态码，还重新查询库存确认没有变化。

T26 验证了另一条事务边界：顾客下单只写订单与明细（`PENDING`），库存不变；只有店员确认收款时才扣库存。两次操作各自是一个完整事务，不会出现“扣了库存但没有订单”的中间态。

### 5.2 SQL 注入为什么无效

T21 把 `' OR 1=1 --` 作为关键词传给 `/api/products`。业务层把它当成普通字符串，数据访问层使用 `LIKE ?` 参数绑定，数据库把整个字符串当作匹配模式（`%' OR 1=1 --%`），因此匹配不到任何商品，返回空列表而不是全部商品。整个过程没有 500 错误，说明参数被正确转义。

### 5.3 三层权限是否一致

| 攻击方式 | 拦截层 | 结果 |
|---|---|---|
| 顾客点“新增商品”按钮 | 页面层根本不渲染按钮 | 无法发起 |
| 顾客直接 POST `/api/products` | 业务层 `require_user("MANAGER")` | 403 |
| 顾客绕过应用直接查 `employee` 表 | 数据库层 `customer_app_role` 无授权 | 拒绝（`regression.sql` 8.2 已验证） |

三层都失效才会越权，这是本设计刻意保留的纵深防御。

### 5.4 测试数据会不会污染正式数据

`setUpModule` 在测试开始前记录：库存表每个商品的当前数量、会员表每位会员的积分、五张表的当前最大主码。`tearDownModule` 先按主码删除测试新增的记录（顺序：明细 → 库存流水 → 积分流水 → 订单 → 库存 → 商品），再把库存与积分写回基线值。因此重复运行测试不会累积脏数据，也不会改变第四周的验收结果。
