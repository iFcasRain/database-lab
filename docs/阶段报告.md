## 2. 项目目标与范围

本项目将小卖部的日常经营活动转换为可运行的关系数据库。v0.1 覆盖商品维护、销售结算、订单与明细、库存状态、会员积分、员工经办、供应商和采购补货，形成“商品 → 销售 → 库存扣减 → 积分更新 → 库存预警 → 采购入库”的最小业务闭环。

进入数据库的信息包括商品、库存、订单、订单明细、会员、积分流水、员工、供应商、采购单、采购明细和库存流水。支付账号、身份证号、监控录像、员工工资、复杂促销、多门店调拨和完整退货审批暂不进入 v0.1，原因是这些信息不属于本阶段最低可运行原型，或存在不必要的隐私和复杂度风险。

## 3. 业务角色与流程

顾客选择商品后，由店员录入商品并校验在售状态和库存。支付成功后，系统生成订单和订单明细，扣减库存，并在会员交易中记录积分变化。库存低于预警值时，库存管理员整理采购需求，店长审批，供应商到货后由库存管理员办理入库。

角色分工如下：

| 角色 | 主要职责 |
|---|---|
| 店长 | 商品维护、员工管理、采购审批、异常处理和经营统计 |
| 店员或收银员 | 商品查询、订单结算、会员识别和积分处理 |
| 库存管理员 | 库存查询、入库、盘点和补货申请 |
| 会员 | 使用本人会员身份、积分和订单信息 |
| 供应商 | 配合供货，不直接操作门店内部数据库 |

## 4. 关系模式设计

数据库包含 12 张业务表：`category`、`product`、`inventory`、`member`、`employee`、`supplier`、`sales_order`、`sales_order_item`、`points_transaction`、`purchase_order`、`purchase_order_item` 和 `inventory_transaction`。

设计遵循以下原则：

1. 每张表只描述一种业务对象或一种明确联系。
2. 订单与订单明细、采购单与采购明细分别拆分，避免重复字段组。
3. 商品当前售价与订单成交单价分开保存，防止调价改变历史交易。
4. 当前库存和积分余额便于快速读取，库存流水和积分流水用于追溯变化。
5. 非会员订单允许 `member_id` 为空，其他业务联系使用外码保证引用有效。
6. 金额使用 `DECIMAL(10,2)`，中文字段使用 `NVARCHAR`，状态使用明确枚举域。

## 5. 主码 候选码与外码

各表使用整数内部编号作为主码。商品编码、条码、会员号、手机号、工号、订单号、采购单号和流水号等具有业务唯一性的字段设置唯一约束，作为候选码。

外码用于保证表间联系：商品引用分类，当前库存引用商品，订单引用会员和收银员，订单明细引用订单和商品，采购单引用供应商与员工，采购明细引用采购单和商品，库存流水引用商品、员工以及相应的销售或采购单据。

## 7. 第四周查询与视图设计

第四周查询围绕完整业务问题设计，包括订单详情、商品销量和销售额、销量阈值、会员消费、超过平均金额的订单、库存补货建议、采购明细和未销售商品。

其中：

- `INNER JOIN` 用于必须存在关联记录的订单明细、商品和员工；
- `LEFT JOIN` 用于保留非会员订单以及当前没有订单的会员；
- `GROUP BY` 和聚合函数用于销量、销售额和消费次数统计；
- `HAVING` 用于筛选累计销量达到阈值的商品；
- 子查询用于比较单笔订单与平均实付金额；
- `NOT EXISTS` 用于查找未出现在已完成订单中的商品。

重复使用的查询封装为 4 个视图：订单详情视图、商品销售统计视图、库存状态视图和会员消费统计视图。

实际运行时，8 组查询全部成功：订单详情返回 5 条明细；商品销售额分别为薯片 11.00 元、牛奶 10.50 元和饮用水 6.00 元；`HAVING` 正确筛选累计销量不少于 3 件的商品；高于平均实付金额的子查询返回 11.00 元订单；纯牛奶库存为 8、预警值为 10，建议补货 12。四个统计视图均创建并查询成功。

## 8. 完整性约束与正反例

数据库使用以下完整性手段：

| 约束类型 | 代表规则 |
|---|---|
| 主码 | 每条商品、订单和流水记录具有唯一内部编号 |
| UNIQUE | 商品编码、条码、会员号、手机号、订单号等不得重复 |
| 外码 | 订单明细必须引用已存在的订单和商品 |
| NOT NULL | 商品名称、价格、订单状态等核心字段不能为空 |
| DEFAULT | 状态、时间、积分和数量具有合理默认值 |
| CHECK | 价格和库存非负、数量大于 0、状态在枚举域内、支付与订单状态一致 |

`constraint.sql` 设计了 1 个合法用例和 7 个非法用例。合法商品与库存应成功通过；负价格、不存在分类、重复条码、负库存、缺少支付方式、零数量明细和错误手机号必须被数据库拒绝。所有测试使用事务回滚，不改变正式样例数据。

实际执行结果中 8 个测试全部为 `PASS`，商品编码以及会员、员工和供应商手机号的 4 个新增格式约束均成功建立。

## 9. 角色权限与正反例

权限遵循最小权限原则：

| 数据库角色 | 允许操作 | 明确禁止或不授予 |
|---|---|---|
| `store_manager_role` | 查看经营数据，维护商品、员工、供应商和采购数据 | 不直接取得服务器级权限 |
| `cashier_role` | 查询商品、库存和会员，处理订单、积分与销售库存变化 | 修改商品售价、删除员工 |
| `inventory_clerk_role` | 查询库存和供应商，处理采购、入库和库存数量 | 查看会员资料和销售订单 |

权限测试同时覆盖正常操作和越权操作。正常查询应成功，收银员改价、库存管理员查看会员资料以及收银员删除员工应失败，以数据库返回的权限错误证明授权真正生效。

首次执行时发现权限拒绝后的事务清理顺序会触发错误 3930，随后将测试调整为先回滚事务再恢复用户身份，并关闭该批次的 `XACT_ABORT`。重新执行后 6 个权限测试全部为 `PASS`，店长、收银员和库存管理员三个角色与演示用户的对应关系正确。
