# v0.1 问题清单（第五周）

第五周的任务之一是带着 ER 模型回头审查 v0.1 的表设计，找出实体遗漏、属性重复、联系表达不清的地方，并说明哪些保留、哪些拟在第六周调整。本清单记录 2026 年 11 月对 v0.1（12 张表、样例数据、视图和角色）逐表复核的结果。

## 1. 复核方法

1. 以[关系模式与数据字典](关系模式与数据字典.md)为基准，逐表核对主码、候选码、外码和域；
2. 以[业务规则映射清单](业务规则映射清单.md)为标尺，逐条检查规则能否被现有结构表达；
3. 用样例数据模拟插入、修改、删除，观察是否产生异常；
4. 把发现的问题按“必须改”“建议改”“保留并记录理由”三类归档。

## 2. 问题清单

| 编号 | 问题 | 业务证据 | 影响 | 改进方向 | 结论 |
|---|---|---|---|---|---|
| P01 | 缺少“应用账号”实体，Web 应用无法登录 | 第 7—9 周需要区分店员与顾客，而 `member` 与 `employee` 都没有口令字段 | 若把口令塞进 `member` 或 `employee`，会让业务表混入认证数据，且一个员工无法拥有多个账号 | 第 6 周新增 `app_user` 表，用可空外码分别关联员工或会员 | **已调整**（第六周） |
| P02 | `sales_order.original_amount`、`discount_amount`、`paid_amount` 是可由明细与规则推导的派生字段 | 三张样例订单的明细合计都等于原价（7.50、11.00、9.00） | 理论上有更新异常：明细变了而订单金额没改 | 保留字段并增加一致性检查；金额在下单事务中一次写入，不允许单独修改 | 保留（反规范化，理由见规范化分析） |
| P03 | `member.points_balance` 与积分流水存在冗余 | `member 201` 的余额 120 = 最后一条流水 `balance_after` | 若只改余额不写流水，账就对不上 | 保留余额用于快速读取，并要求流水与余额同事务更新 | 保留 + 约束与回归校验 |
| P04 | `inventory.quantity` 与库存流水存在冗余 | 样例订单的三条出库流水与库存变化一致 | 若盘点时只改数量不写流水，无法追溯 | 保留数量，要求写流水；第 6 周补充索引 | 保留 + 事务约束 |
| P05 | 商品与库存是一对一强依赖，但数据库无法强制“新增商品必须同时有库存” | 3 个商品都有对应库存记录 | 若只插商品不插库存，`vw_inventory_status` 会漏掉该商品 | 应用层用事务同时插入两条记录 | 已解决（第七至九周代码保证） |
| P06 | 订单“至少一条明细”无法由外码保证 | 5 条明细分布在 3 张订单上，样例满足规则 | 极端情况下可能出现空订单 | 下单事务与回归脚本共同保证 | 保留，记录为已知限制 |
| P07 | 同一订单同一商品只能出现一次，但业务上顾客可能分两次扫码 | 样例数据每个订单内商品不重复 | 若前端逐次插入而不合并，会撞唯一约束 | 提交前按商品合并数量；冲突时返回友好提示 | 已解决（`_parse_items`） |
| P08 | `employee.job_type` 与数据库角色容易混淆 | 第四周角色是 `cashier_role` 等，`job_type` 是 `CASHIER` 等 | 可能误以为改了 `job_type` 就改了权限 | 明确：`job_type` 是业务岗位，权限由数据库角色控制；应用账号的 `role` 与数据库角色一一对应 | 保留，已在文档中区分 |
| P09 | 缺少“顾客只能看自己订单”的行级安全 | 顾客账号在数据库中拥有 `sales_order` 的 SELECT 授权 | 绕过应用直接查表可看到全部订单 | 当前由业务层过滤；后续可启用 SQL Server 行级安全 | 记录为限制（v1.0 未启用 RLS） |
| P10 | `member.phone`、`employee.phone` 设为唯一，家庭共用手机号时会冲突 | 样例中 3 位会员手机号各不相同 | 特殊场景下无法录入第二位家庭成员 | 当前门店规模可接受；若需要可在后续版本改为“手机号 + 会员号”联合候选码 | 保留 |
| P11 | 采购单与采购明细有完整结构，但没有对应的应用界面 | `purchase_order` 有 3 条样例数据 | 补货流程只能靠 SQL 脚本完成 | v1.0 应用先覆盖商品、库存、订单；采购界面列为后续工作 | 暂缓（超出本周范围） |
| P12 | `sales_order_item` 复合唯一约束会阻止同一商品分两行（例如不同优惠） | 样例中不存在该情况 | 若将来支持单品优惠，需要调整约束 | 当前业务规则明确“同商品合并”，保留约束 | 保留 |
| P13 | `points_transaction.order_id` 可空且不唯一，容易被误当作“一单一流水” | 订单 5001 有 REDEEM 与 EARN 两条流水 | 若按订单号去重统计会漏数据 | 文档明确“一笔订单最多两条流水”；统计按流水条数计算 | 保留 |
| P14 | 缺少按会员、按状态的常用查询索引 | 第四周查询在 3 张订单上无感知 | 数据量增大后列表与统计会变慢 | 第 6 周补充 7 个索引 | 已调整（第六周） |
| P15 | 供应商名称重复没有约束 | 样例 3 个供应商名称不同 | 重名供应商难以区分 | 用 `supplier_code` 区分，名称不设唯一 | 保留 |

## 3. 按结论分类

### 3.1 保留并记录理由

- P02、P03、P04：派生字段属于为提高读取效率而做的反规范化，配合事务与回归检查使用；
- P08：业务岗位与数据库权限本来就应当分层；
- P10、P12、P13、P15：与当前单门店业务规则一致，改为其他形式反而增加复杂度。

### 3.2 第六周调整

- P01：新增 `app_user` 表与相关约束；
- P14：补充索引；
- 顺带补充 3 个只读视图（`vw_product_catalog`、`vw_active_cashier`、`vw_order_summary`），让权限受限的角色也能看到完整信息；
- 新增 2 个数据库角色和 5 个应用账号，把界面权限收敛到数据库一侧。

以上改动均为“新增”，不修改、不删除 v0.1 已有的任何表、字段、约束和数据，迁移前后的关键查询结果由 `regression.sql` 逐项比对。

### 3.3 记录为已知限制

- P06：订单至少一条明细由代码保证；
- P09：未启用行级安全，顾客订单隔离由业务层实现；
- P11：采购流程暂无应用界面。

## 4. 复核结论

v0.1 的 12 张表在实体划分、码设计和外码方向上没有发现需要拆分或合并的结构性问题，规范化分析（见[函数依赖与规范化分析](函数依赖与规范化分析.md)）也支持这一结论。真正缺少的是与 Web 应用相关的账号实体和查询索引，这两项在第六周以“只增不改”的方式补齐。
