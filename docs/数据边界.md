# 小卖部数据边界

## 1. 目的

需求分析阶段先划定数据边界：明确哪些信息进入数据库、哪些不进入，避免把无关或无法结构化的信息混入后续的数据表设计。

## 2. 进库信息

| 信息 | 进库？ | 理由 |
| --- | --- | --- |
| 商品（名称、条码、分类、当前售价、在售状态） | ✅ | 交易录入与校验、库存、定价都依赖商品主数据 |
| 库存（数量、预警值） | ✅ | 校验可售数量、扣减库存、低库存预警与补货决策 |
| 订单（单号、交易时间、经办店员、会员、实付金额、付款方式、状态） | ✅ | 记录每笔交易；状态区分待支付 / 已完成 / 已取消 |
| 订单明细（商品、数量、成交单价） | ✅ | 记录「交易当时」的商品与价格，支撑销售统计与退货核对 |
| 会员（卡号、资料、当前积分） | ✅ | 识别会员、查询可用积分、按规则积分抵扣 |
| 积分流水（会员、关联交易、使用/累积、时间） | ✅ | 积分变动须可追溯，不能只存余额 |
| 员工（工号、姓名、角色） | ✅ | 订单记录经办店员；店长管理员工与角色、支撑权限控制 |
| 供应商（名称、联系方式） | ✅ | 补货采购需联系供货、到货核对（仅作参考数据，无操作权限） |
| 补货需求（商品、数量、提交人、审核人、状态） | ✅ | 支撑库存管理员提交、店长审核的补货流程 |
| 入库记录（到货商品、数量、核对结果、时间） | ✅ | 到货核对后增加库存，须留下入库来源 |
| 库存变动记录（类型、商品、数量、关联单据、时间） | ✅ | 销售扣减 / 入库 / 盘点 / 退货的库存变动可追溯、可核对 |
| 盘点记录（盘点人、时间、系统数、实盘数、差异、原因、审核） | ✅ | 盘点差异需记录原因并交店长审核后再调整 |
| 退货/退款记录（原订单、退货商品、退款金额、审核、库存与积分调整） | ✅ | 交易后退货需单独记录退款、库存与积分变化 |

## 3. 不进库信息

| 信息 | 进库？ | 理由 |
| --- | --- | --- |
| 门店装修风格、货架陈列布局 | ❌ | 与交易、库存、权限、经营决策无关 |
| 员工心情、当班精神状态 | ❌ | 无法结构化，且与经营数据无关 |
| 顾客线下逛店路径、停留时间 | ❌ | 线下场景无法采集与结构化，不属于交易数据 |
| 商品生产/加工的具体工艺、配方细节 | ❌ | 小卖部销售成品、无加工环节；即使有也属非结构化经营数据 |
| 供应商内部经营数据、供货车辆等细节 | ❌ | 与门店经营无关，供应商仅参与供货协作 |
| 促销广告文案、海报图片素材 | ❌ | 属营销素材、非结构化；如需营销模块再单独考虑 |

## 4. 补充说明

- **成交单价 ≠ 当前售价**：订单明细存「交易当时的成交单价」作为历史快照，商品表存「当前售价」，两者分开，否则改价后历史订单对不上。
- **积分要「余额 + 流水」**：会员表存当前积分余额，积分流水表存每笔使用/累积，才能追溯变动。
- **供应商只入库参考信息**：供应商信息作为参考数据入库，但供应商本身没有系统操作权限（见角色清单「外部角色隔离」）。
- **低库存提醒可实时计算**：由「库存 < 预警值」派生，若不需追踪「已提醒/已处理」状态则不必单独落表。
