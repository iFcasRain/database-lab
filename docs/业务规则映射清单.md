# 业务规则与映射清单（第五周）

本清单把 ER 图中的每条联系展开成可检查的业务规则：两端的最小/最大基数、适用条件、对应的表与外码，以及这条规则目前由数据库约束、应用代码还是人工检查来保证。第 7—9 周的应用实现必须与这张表保持一致。

## 1. 编号约定

- `BR`：Business Rule，业务规则。
- “实现方式”三选一：`约束`（主码、唯一、外码、检查约束）、`代码`（后端业务层）、`人工`（脚本或操作规范）。
- “验证”列指向第三周约束脚本、第四周权限脚本、第六周回归脚本或应用测试脚本中的具体用例。

## 3. 最小/最大基数的读法

以 BR09 为例，ER 图中 SALES_ORDER 与 SALES_ORDER_ITEM 的连线两端标注为 `1` 和 `N`：

- 从订单看向明细：一张订单对应 **1 到 N** 条明细（最小 1，最大 N）—— 这就是“订单至少一条明细”。
- 从明细看向订单：一条明细对应 **恰好 1** 张订单（最小 1，最大 1）。

再以 BR13 为例，MEMBER 与 SALES_ORDER 的连线两端是 `0..1` 和 `N`：

- 从会员看向订单：一个会员可以有 0 到 N 张订单。
- 从订单看向会员：一张订单最多对应 1 个会员，也可以是 0 个（散客）。

## 4. 与本清单相关的已知缺口

| 缺口 | 说明 | 处理 |
|---|---|---|
| 行级安全 | 数据库未启用 Row-Level Security，顾客若绕过应用直接查表可以看到全部订单 | 当前由业务层按 `member_id` 过滤，已在 BR26 与设计文档中标注为限制 |
| “至少一条明细”无法由纯外码保证 | 外码只能保证明细指向已存在的订单 | 由下单事务、回归脚本和应用测试共同保证 |
| 采购入库尚未提供应用界面 | 采购流程目前由 SQL 脚本完成 | v1.0 应用聚焦商品、库存、订单与明细，采购界面列为后续工作 |
