## 3. ER 模型与设计说明

### 3.1 实体与标识

v1.0 共有 13 个实体：商品分类、商品、当前库存、供应商、采购单、采购明细、会员、员工、销售订单、订单明细、积分流水、库存流水和应用账号。每个实体使用整数代理码作为主码，业务上能唯一识别记录的属性（商品编码、条码、会员号、手机号、工号、订单号、采购单号、流水号、用户名）设置为候选码。

订单明细与采购明细使用复合候选码 (`order_id`, `product_id`) 与 (`purchase_order_id`, `product_id`)，表达“同一单据内同一商品只出现一次”的业务规则。

### 3.2 联系与基数

| 联系 | 基数 | 参与约束 |
|---|---|---|
| 分类—商品 | 1:N | 商品必须属于一个分类 |
| 商品—库存 | 1:1 | 商品必须有且只有一条库存记录 |
| 会员—订单 | 1:N | 订单可以是散客（0..1） |
| 员工—订单 | 1:N | 订单必须有经办收银员 |
| 订单—明细 | 1:N | 订单至少一条明细（由事务保证） |
| 商品—明细 | 1:N | 明细必须有商品 |
| 会员—积分流水 | 1:N | 流水必须有会员 |
| 订单—积分流水 | 1:N（可空） | 一笔订单最多两条流水 |
| 供应商—采购单 | 1:N | 采购单必须有供应商 |
| 采购单—采购明细 | 1:N | 采购单至少一条明细 |
| 商品—库存流水 | 1:N | 流水必须有商品 |
| 员工/订单/采购单—库存流水 | 1:N | 按变动类型关联来源单据 |
| 员工/会员—应用账号 | 0..1 / 0..N | 账号必须且只能关联其一 |

完整清单见[ER模型与ER图](ER模型与ER图.md)与[业务规则映射清单](业务规则映射清单.md)（26 条业务规则）。

### 3.3 设计要点

1. **商品与库存拆分**：修改频率、责任人和授权对象不同；价格变动不产生库存流水，盘点不修改价格。
2. **订单与明细拆分**：避免重复组（1NF）与订单级属性的更新异常；明细保存成交单价，保护历史交易。
3. **当前值与流水并存**：`inventory.quantity`、`member.points_balance` 是当前状态，流水是变化依据，两者同事务更新。
4. **应用账号独立**：登录信息不混入员工或会员表，一个员工或会员可以没有账号，也可以显式停用。

## 4. 规范化与迁移

### 4.1 规范化结论

逐表分析 13 张表的候选码、函数依赖与更新异常后，结论是**全部满足 3NF 与 BCNF，无需拆分**。v0.1 在设计时已经避免了典型的传递依赖：商品表不冗余分类名称，订单明细不读取商品当前售价，积分流水保存 `balance_after` 快照。

保留下来的冗余属于有意的反规范化：

| 冗余 | 保留理由 | 一致性保证 |
|---|---|---|
| `sales_order.original_amount` / `discount_amount` / `paid_amount` | 列表与对账无需聚合明细 | 下单事务一次写入；检查约束 + 回归检查 |
| `member.points_balance` | 结算时快速读取余额 | 与流水同事务更新；回归校验 |
| `inventory.quantity` | 下单与库存页快速读取 | 与流水同事务更新；非负约束 |
| `app_user.display_name` | 登录后直接显示，避免联查 | 迁移时按姓名写入，仅用于显示 |

### 4.2 迁移内容

`migration.sql` 只做“新增”，不改动 12 张既有表的任何字段、约束和数据：

- 新增 `app_user` 表（5 个演示账号）；
- 新增 3 个只读视图：`vw_product_catalog`、`vw_active_cashier`、`vw_order_summary`；
- 新增 2 个数据库角色与 5 个应用账号，并按最小权限授权；
- 补充 7 个索引；
- 为第四周角色补充应用所需的少量权限（只增不减）。

### 4.3 回归结果

`regression.sql` 共 23 项检查，覆盖结构、数据、金额、销量、库存、积分、账号与权限，实际执行 **23 项全部 PASS**，输出“v1.0 回归通过”。迁移前后关键查询（订单金额、明细合计、商品销量、库存数量）完全一致，说明业务含义未变。

## 5. Web 应用实现

### 5.1 分层结构

```text
页面层  app/web/ + templates + static
   ↓ 调用
业务层  app/services/
   ↓ 调用
数据访问层 app/db/
   ↓ pyodbc（参数化 SQL）
数据库层 SQL Server（表、约束、视图、角色）
```

- 页面层只负责接收请求、校验展示与调用业务层，不出现 SQL；
- 业务层负责业务规则、事务边界与角色范围；
- 数据访问层集中所有 SQL，统一管理连接、参数、事务与驱动异常翻译。

### 5.2 关键实现

| 需求 | 实现 |
|---|---|
| 连接打开与关闭 | `app/db/connection.py` 的 `connection()` 上下文管理器，请求结束即关闭并禁用连接池 |
| 权限收敛 | 连接建立后 `EXECUTE AS USER = 'app_xxx'`，按登录角色切换数据库应用账号 |
| 参数绑定 | 全部 SQL 使用 `?`；标识符只取代码内白名单 |
| 事务管理 | `transaction()` 显式 `BEGIN / COMMIT / ROLLBACK` |
| 下单闭环 | 订单 + 明细 + 库存扣减 + 库存流水 + 积分流水 + 会员余额，同一事务 |
| 超卖防护 | 库存行 `WITH (UPDLOCK, ROWLOCK)` |
| 统一异常 | `AppError` 家族 + 全局 `errorhandler`，10 个稳定错误码 |
| 日志追踪 | 请求号贯穿日志，详细原因只写日志 |
| 角色界面 | 顾客 / 店员 / 库存管理员 / 店长四套导航与按钮 |

### 5.3 角色业务流程

| 角色 | 可执行操作 | 典型流程 |
|---|---|---|
| 顾客 | 浏览在售商品、线上下单、查看本人订单与积分、取消未付款订单 | 登录 → 选商品 → 提交（`PENDING`）→ 查看状态 |
| 店员 | 商品查询、会员识别、门店结算下单、确认收款、取消订单 | 登录 → 加入清单 → 选会员与支付方式 → 提交（`COMPLETED`，扣库存、结算积分） |
| 库存管理员 | 库存查询、盘点调整 | 登录 → 查看低库存 → 盘点调整（写盘盈/盘亏流水） |
| 店长 | 以上全部 + 商品维护 + 经营分析 | 登录 → 新增/编辑商品 → 查看报表 |

## 6. 测试

| 测试 | 范围 | 结果 |
|---|---|---|
| `regression.sql` | 数据库迁移后的结构、数据与权限 | 23 项 PASS |
| `tests/test_app.py` | 应用登录、权限、参数、事务、库存、报表 | 34 项 PASS |
| 手工浏览器验收 | 四个角色的完整流程 | 全部按预期 |

重点结论：

1. 库存不足时整体回滚，不产生半张订单；
2. 顾客线上下单不扣库存，确认收款时才扣；
3. 参数化查询使注入字符串失去 SQL 语义；
4. 三层权限（页面 / 业务 / 数据库）同时生效；
5. 测试结束后样例数据自动还原。

## 7. AI 使用与人工验证

AI 参与的工作与人工修改记录在 [ai_log.md](../ai_log.md) 第 8—10 节。总体原则：

- AI 用于梳理实体与联系、生成脚本与代码初稿、提出测试用例；
- 结构决策（是否拆表、是否保留冗余）由组员依据业务规则确认；
- 所有 SQL 与接口都在真实 SQL Server 与浏览器中运行验证，语法正确不等于业务正确；
- AI 生成的错误在验证阶段被发现并修正（例如 `EXECUTE AS USER` 必须使用字符串常量、会话缓存导致用户对象被误缓存等），过程记录在 ai_log。

## 8. 实验总结

第 5—9 周把前四周的数据库原型推进为一个可运行的应用系统：

1. **设计层面**：ER 模型与规范化分析证明 v0.1 的 12 张表结构合理，需要补充的是应用账号、查询索引和受控视图，迁移以“只增不改”的方式完成，风险可控；
2. **实现层面**：分层结构让“改一行业务规则”和“改一条 SQL”互不影响；数据访问层统一收敛了权限、参数化与异常，页面层几乎不含重复逻辑；
3. **安全层面**：三层权限 + 参数化 + 口令摘要 + 统一错误提示，把常见的学生项目漏洞（拼接 SQL、越权、错误信息泄露）都堵住了；
4. **工程层面**：脚本可重复执行、测试可重复运行且自动清理、日志可按请求号追踪，其他同学按复现说明可以从零跑通。

不足之处也很明确：采购流程尚未提供界面、未启用行级安全、单号生成在高并发下可能冲突。这些都在设计文档的“已知限制”中列明，属于后续可以继续做的方向。
