# v1.0 Web 应用设计与实现说明（第 7—9 周）

## 1. 目标与范围

在 v1.0 数据库之上，用 Web 应用框架实现一个可操作的界面程序，完成“登录 → 商品/库存/订单操作 → 数据写入”的完整流程，并保证：

1. 程序严格按“页面层 → 业务层 → 数据访问层 → 数据库层”分层；
2. 所有 SQL 只在数据访问层出现，且一律参数化；
3. 下单、确认收款、库存盘点等写操作使用显式事务，失败整体回滚；
4. 界面权限、后端权限与数据库权限三者一致；
5. 异常由后端统一处理，前端只看到友好提示，详细原因进日志。

技术选型：Python 3.12 + Flask 3.1 + pyodbc 5.x + SQL Server 17（`.\SQLEXPRESS`）。选择 Flask 的原因是它足够轻量，路由、模板和错误处理都能直接对应讲义里的三层结构，不会把业务逻辑藏进框架约定里。

| 层 | 目录 | 只做什么 | 明确禁止 |
|---|---|---|---|
| 页面层 | `app/web/`、`app/templates/`、`app/static/` | 接收请求、解析参数、调用业务层、渲染页面或返回 JSON | 写 SQL、直接用 pyodbc、自己判断业务规则 |
| 业务层 | `app/services/` | 校验输入、判断业务规则、控制事务、组织多次数据访问 | 拼接 SQL、直接渲染 HTML |
| 数据访问层 | `app/db/` | 建立连接、切换权限、参数化执行 SQL、转换结果、翻译驱动异常 | 判断业务规则、处理 HTTP |
| 数据库层 | SQL Server | 保存表、约束、视图、角色与权限 | — |

检查方法：在 `database-lab` 目录执行 `grep -rn "pyodbc" app/` 只会命中 `app/db/`；执行 `grep -rn "SELECT \|INSERT INTO\|UPDATE dbo" app/services app/web` 不会命中业务代码。

## 3. 一次查询经过哪些层

以店员打开“商品”页面为例：

```text
浏览器 GET /products?keyword=牛奶
  → 页面层  app/web/pages.py: products()
      读取 query 参数，调用 product_service.list_products(user, keyword=...)
  → 业务层  app/services/product_service.py: list_products()
      取当前用户角色，决定是否只返回在售商品，打开只读连接
  → 数据访问层 app/db/connection.py: connection("CASHIER")
      建立连接 → EXECUTE AS USER = 'app_cashier'（数据库权限收敛）
  → 数据访问层 app/db/product_dao.py: list_products()
      cursor.execute("... WHERE product_name LIKE ? ...", (like, like, like))
  → 数据库层 SQL Server
      以 app_cashier 的权限查询 vw_product_catalog
  → 结果逐层返回：dict 列表 → Jinja 模板 → HTML
```

对应接口版本：`GET /api/products?keyword=牛奶` 走 `app/web/api.py: products()`，业务层与数据访问层完全相同，只是最后返回 JSON 而不是 HTML。

## 4. 一次修改经过哪些层

以“店员结算下单”为例，这是本应用最重要的事务：

```text
POST /api/orders {items:[{product_id:101,quantity:2}], payment_method:"CASH", member_no:"M001"}
  → 页面层  api.py: order_create()         读取 JSON，调用业务层
  → 业务层  order_service.create_order()
      ├─ validation 校验数量、支付方式、积分
      ├─ transaction("CASHIER") 开启显式事务：BEGIN TRANSACTION
      ├─ product_dao.get_product()        读取商品状态与当前售价（不信任前端价格）
      ├─ inventory_dao.lock_quantity()    WITH (UPDLOCK, ROWLOCK) 锁定库存行
      ├─ 校验库存是否充足（不足 → 抛业务异常 → 整体回滚）
      ├─ member_dao.find_by_member_no()   会员校验
      ├─ 计算 discount / paid / earn      积分规则
      ├─ order_dao.insert_order()         OUTPUT INSERTED.order_id
      ├─ order_dao.insert_item()          逐条写明细
      ├─ inventory_dao.decrease_quantity() + insert_transaction(SALE_OUT)
      ├─ member_dao.insert_points_transaction(REDEEM/EARN) + update_points
      └─ COMMIT TRANSACTION（任一步异常 → ROLLBACK）
  → 返回订单详情 → 前端跳转 /orders/<id>
```

顾客线上下单的事务边界不同：只写订单（`PENDING`）与明细，不扣库存、不结算积分；等店员确认收款时再扣库存、结算积分。这样“下单”和“付款”两个业务动作各自是一个完整事务。

## 5. 数据访问层设计

### 5.1 连接与权限收敛

```python
with connection("CASHIER") as conn:      # 只读
    ...
with transaction("MANAGER") as conn:     # 写操作
    ...
```

1. 用配置中的连接串打开连接（默认 Windows 身份验证，口令不写进代码）；
2. 立即执行 `EXECUTE AS USER = 'app_cashier'`，把会话切换成迁移脚本创建的 `WITHOUT LOGIN` 应用账号；
3. 之后这条连接上的一切 SQL 都受该账号在数据库中的真实授权约束；
4. 请求结束即关闭连接，并关闭 pyodbc 连接池，避免身份上下文串到下一个请求。

角色与应用账号的映射：

| 登录角色 | 应用账号 | 所属数据库角色 | 主要授权 |
|---|---|---|---|
| 登录校验 | `app_auth` | `auth_lookup_role` | `SELECT app_user`、`UPDATE(last_login_at)` |
| CUSTOMER | `app_customer` | `customer_app_role` | 商品目录、本人订单/积分、插入订单与明细 |
| CASHIER | `app_cashier` | `cashier_role`（第四周） | 商品、库存、会员查询；订单写入与更新 |
| INVENTORY | `app_inventory` | `inventory_clerk_role`（第四周） | 库存查询与数量更新；采购 |
| MANAGER | `app_manager` | `store_manager_role`（第四周） | 全部经营数据、商品维护、代班收银 |

### 5.2 参数化查询

所有 SQL 使用 `?` 占位符，例如：

```python
sql = "SELECT ... FROM dbo.vw_product_catalog WHERE 1 = 1"
if keyword:
    sql += " AND (product_name LIKE ? OR product_code LIKE ? OR barcode LIKE ?)"
    params.extend([like, like, like])
cursor.execute(sql, tuple(params))
```

表名、列名等标识符只取自代码中的常量白名单（例如 `product_dao.update_product` 的列清单），不来自用户输入。唯一需要拼接标识符的地方是 `EXECUTE AS USER`，拼接前用正则 `^[A-Za-z_][A-Za-z0-9_]*$` 校验，并且只接受配置里的值。

### 5.3 事务边界

`app/db/connection.py` 的 `transaction()` 负责：

1. 打开连接并切换应用账号；
2. 执行 `BEGIN TRANSACTION`；
3. 正常结束时 `COMMIT TRANSACTION`；
4. 任何异常时执行 `IF @@TRANCOUNT > 0 ROLLBACK TRANSACTION`，再把异常抛给上层；
5. 无论成功失败都关闭游标与连接。

不使用 `-b` 或“自动提交 + 逐条提交”的方式，因为下单必须“订单、明细、库存、流水、积分”同时成功或同时失败。

### 5.4 驱动异常翻译

`app/db/base.py` 是唯一 import `pyodbc` 异常的地方：

| 驱动异常 | 翻译为 | 前端看到的提示 |
|---|---|---|
| `pyodbc.IntegrityError`（23000） | `CONSTRAINT_CONFLICT` | 数据与数据库约束冲突，请检查输入内容 |
| `pyodbc.ProgrammingError` 且消息含权限关键字 | `FORBIDDEN` | 当前角色无权执行该操作 |
| `pyodbc.OperationalError`（连接失败） | `DATABASE_UNAVAILABLE` | 系统暂时无法完成操作，请稍后再试 |
| 其他 `pyodbc.DatabaseError` | `INTERNAL_ERROR` | 系统暂时无法完成操作，请稍后再试 |

原始错误信息只写入日志的 `detail` 字段，不返回给前端。

### 5.5 结果转换

`rows_to_dicts()` 把元组结果转成字典，并把 `Decimal` 转成 `float`（金额仍用 `DECIMAL(10,2)` 存储在数据库中，转换只发生在出参环节，避免 JSON 序列化问题）。

## 6. 业务层设计

| 业务 | 主要规则 | 事务 |
|---|---|---|
| 登录 | 用户名/口令非空；口令 PBKDF2 校验；账号必须启用 | 否（单条查询 + 单条更新） |
| 商品查询 | 顾客只看在售商品；其他角色可按状态筛选 | 否 |
| 商品新增 | 仅店长；编码格式 `P+3 位数字`；条码 8—32 位数字；编码/条码不得重复；分类必须存在且在用；同时建立库存记录 | 是 |
| 商品修改 | 仅店长；分类存在性校验；不允许改编码与条码 | 是 |
| 库存查询 | 店员、库存管理员、店长可见 | 否 |
| 库存盘点 | 仅库存管理员与店长；数量不得为负；数量无变化时拒绝；写 `COUNT_GAIN` / `COUNT_LOSS` 流水 | 是 |
| 门店下单 | 店员/店长；商品必须存在且在售；库存充足（`UPDLOCK` 锁定）；金额按数据库价格重算；积分抵扣为 10 的倍数且不超过余额与订单金额 | 是 |
| 顾客线上下单 | 顾客；自动指派当班收银员；只写订单与明细，状态 `PENDING`，不扣库存 | 是 |
| 确认收款 | 店员/店长；只处理 `PENDING`；重新校验库存；扣库存、写流水、结算积分 | 是 |
| 取消订单 | 顾客只能取消自己的 `PENDING` 订单；店员/店长可取消任意 `PENDING` 订单 | 是 |
| 订单查询 | 顾客只见本人订单；库存管理员不可见订单 | 否 |
| 会员查询 | 店员与店长；顾客只能看本人 | 否 |
| 经营分析 | 仅店长 | 否 |

积分规则（与样例数据一致）：

- 每消费 1 元获得 1 分（向下取整）；
- 每 10 分抵扣 1 元，抵扣金额不得超过订单金额；
- 一笔会员订单最多产生两条流水：先 `REDEEM` 后 `EARN`。

## 8. 角色权限矩阵（三层对照）

| 功能 | 顾客 | 店员 | 库存管理员 | 店长 | 数据库层保证 |
|---|:--:|:--:|:--:|:--:|---|
| 浏览在售商品 | ✓ | ✓ | ✓ | ✓ | 四个角色都有 `vw_product_catalog` 的 SELECT |
| 新增/修改商品 | ✗ | ✗ | ✗ | ✓ | 仅 `store_manager_role` 有 product 的 INSERT/UPDATE；顾客被显式 DENY |
| 查看库存 | ✓（仅目录数量） | ✓ | ✓ | ✓ | 顾客只能读目录视图，没有 `inventory` 基表授权 |
| 库存盘点 | ✗ | ✗ | ✓ | ✓ | 只有这两个角色有 `inventory.quantity` 的 UPDATE |
| 门店结算下单 | ✗ | ✓ | ✗ | ✓ | `sales_order` 的 INSERT 授权 |
| 线上下单 | ✓ | — | ✗ | — | `customer_app_role` 有 `sales_order` INSERT |
| 确认收款 | ✗ | ✓ | ✗ | ✓ | `sales_order` 的 UPDATE 授权 |
| 取消订单 | 仅本人 | ✓ | ✗ | ✓ | 顾客只有 `UPDATE(order_status)` 的列级授权 |
| 查看订单 | 仅本人 | 全部 | ✗ | 全部 | `inventory_clerk_role` 被 DENY `sales_order` 的 SELECT |
| 查看会员资料 | 仅本人 | ✓ | ✗ | ✓ | `inventory_clerk_role` 被 DENY `member` 的 SELECT |
| 经营分析 | ✗ | ✗ | ✗ | ✓ | 只有店长有统计视图与全部基表读取 |

三层同时生效：页面按角色隐藏按钮，业务层用 `require_user(...)` 再拦一次，数据库用角色授权做最后一道闸门。即使绕过前端直接调接口，业务层仍会拒绝；即使绕过应用直接连库，数据库权限仍会拒绝（回归脚本用 `EXECUTE AS USER` 验证了这一点）。

## 9. 统一异常处理与错误码

所有业务异常继承 `AppError`，由 `app/__init__.py` 中的 `@app.errorhandler(AppError)` 统一处理：

```json
{
  "success": false,
  "error": {"code": "VALIDATION_ERROR", "message": "购买数量不能小于 1", "fields": {"items": "至少一件"}},
  "request_id": "8f3a1c92b0d4"
}
```

| 错误码 | HTTP | 触发场景 | 前端提示 |
|---|---:|---|---|
| `VALIDATION_ERROR` | 400 | 参数缺失、格式错误、超出范围 | 具体字段提示 |
| `AUTH_REQUIRED` | 401 | 未登录或会话失效 | 请先登录后再操作 |
| `AUTH_FAILED` | 401 | 用户名或口令错误 | 用户名或密码不正确 |
| `FORBIDDEN` | 403 | 角色无权、数据库拒绝 | 当前角色无权执行该操作 |
| `NOT_FOUND` | 404 | 商品/订单/会员不存在 | 没有找到对应的数据 |
| `BUSINESS_RULE_VIOLATION` | 409 | 库存不足、状态不允许、积分不足 | 具体业务原因 |
| `CONSTRAINT_CONFLICT` | 409 | 唯一键、外码、检查约束冲突 | 数据与数据库约束冲突，请检查输入内容 |
| `DATABASE_UNAVAILABLE` | 503 | 连接失败、实例不可用 | 系统暂时无法完成操作，请稍后再试 |
| `CONFIGURATION_ERROR` | 500 | 未执行迁移、应用账号缺失 | 系统配置不完整，请联系管理员 |
| `INTERNAL_ERROR` | 500 | 未预期异常 | 系统暂时无法完成操作，请稍后再试 |

页面请求遇到异常时渲染 `error.html`，显示错误码与请求号，不显示 SQL、表名、堆栈或连接信息。

## 10. 日志与请求追踪

- 每个请求生成 12 位 `request_id`，写入响应头 `X-Request-Id`，并出现在该请求的所有日志中；
- 日志格式：`时间 | 级别 | req=请求号 | user=用户名 | role=角色 | 模块 | 内容`；
- 记录内容：登录成败、业务异常的错误码与原因、请求完成的方法/路径/状态/耗时；
- 详细原因（数据库原始错误、约束名）写入 `detail`，只进日志不进响应；
- 日志文件：`logs/app.log`，2 MB 滚动、保留 5 份。

示例（真实输出）：


## 11. 安全措施

| 风险 | 措施 | 位置 |
|---|---|---|
| SQL 注入 | 全部使用 `?` 参数；标识符只取常量白名单 | `app/db/*` |
| 口令泄露 | PBKDF2-SHA256（20 万次迭代）+ 随机盐，只存摘要；比较用 `hmac.compare_digest` | `app/security.py` |
| 会话劫持 | `HttpOnly` + `SameSite=Lax` 会话；会话超时 1 小时；登录时清空旧会话 | `app/config.py`、`security.py` |
| 越权 | 三层校验：页面隐藏 + 业务层 `require_user` + 数据库角色授权 | `app/services/*`、`sql/migration.sql` |
| 数据库账号过权 | 应用不使用 sa，按角色切换到最小权限账号 | `app/db/connection.py` |
| 错误信息泄露 | 统一错误码与友好提示，原始信息只进日志 | `app/errors.py`、`app/__init__.py` |
| 金额篡改 | 服务端按数据库价格重算，忽略前端传来的金额 | `order_service._collect_lines` |
| 超卖 | 下单时 `WITH (UPDLOCK, ROWLOCK)` 锁定库存行 | `inventory_dao.lock_quantity` |
| 重复提交 | 确认收款带 `order_status = 'PENDING'` 条件更新，重复确认返回业务异常 | `order_dao.complete_order` |

## 12. 已知限制

1. 未启用 SQL Server 行级安全，顾客订单隔离由业务层按 `member_id` 过滤实现；
2. 采购单与采购入库暂未提供界面，仍通过 SQL 脚本完成；
3. 单号生成依赖“当日最大号 + 1”，高并发下理论上可能撞唯一约束，此时返回冲突提示；
4. 未实现验证码、登录失败锁定等增强措施，属于课程项目范围之外。
