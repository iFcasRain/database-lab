# 小卖部数据边界清单

## 1. 边界说明

本项目面向一家线下单门店小卖部，v0.1 原型只处理商品销售、库存、会员积分、员工经办、供应商和补货等核心经营活动。判断一项信息是否进入数据库，主要看它是否用于交易记录、库存核对、经营决策、权限控制或责任追溯。

## 2. 进入数据库的信息

| 信息类别 | 主要内容 | 进入数据库的理由 |
|---|---|---|
| 商品分类 | 分类编号、分类编码、分类名称、启用状态 | 便于组织商品和进行分类销售统计 |
| 商品 | 商品编号、商品编码、条码、名称、分类、单位、售价、销售状态 | 是销售、库存和补货业务的基础 |
| 当前库存 | 商品、现存数量、预警数量、更新时间 | 支持销售校验、库存预警和补货决策 |
| 库存变动 | 商品、变动类型、变动数量、关联订单或采购单、经办人、时间 | 解释库存为什么增加或减少，便于追溯和盘点 |
| 销售订单 | 订单号、会员、收银员、交易时间、状态、支付方式、金额 | 记录每笔交易的整体信息并支持经营统计 |
| 销售订单明细 | 订单、商品、数量、成交单价 | 记录一笔订单具体购买了哪些商品 |
| 会员 | 会员号、姓名、手机号、积分余额、注册时间、状态 | 支持会员识别、积分累计和会员消费查询 |
| 积分流水 | 会员、关联订单、变动类型、变动值、变动后余额、时间 | 避免只保存积分余额而无法解释积分来源和去向 |
| 员工 | 工号、姓名、手机号、岗位、入职日期、状态 | 支持经办责任追溯和后续角色权限划分 |
| 供应商 | 供应商编码、名称、联系人、联系电话、状态 | 支持补货来源记录和采购协作 |
| 采购单 | 采购单号、供应商、创建人、审批人、日期、状态、金额 | 记录补货申请、审批和到货过程 |
| 采购单明细 | 采购单、商品、订购数量、实收数量、进价 | 记录每次补货涉及的商品和数量 |

## 3. 暂不进入数据库的信息

| 信息 | 暂不进入的理由 | 后续处理方式 |
|---|---|---|
| 顾客在货架前的浏览轨迹、停留时间 | v0.1 没有客流采集设备，也不是完成交易所必需 | 后续确有客流分析需求时再扩展 |
| 顾客身份证号、家庭住址等敏感信息 | 会员识别不需要收集这些信息，收集会扩大隐私风险 | 只保存完成会员业务所需的最少信息 |
| 银行卡号、支付账号、支付密码 | 门店数据库不应保存支付凭证和敏感账户信息 | 仅记录支付方式和支付结果 |
| 员工工资、考勤和绩效 | 属于人事管理范围，不属于本阶段经营数据库核心闭环 | 后续可建设独立人事模块 |
| 门店装修风格、背景音乐、员工心情 | 难以结构化且与交易、库存和权限没有直接关系 | 不纳入本项目 |
| 商品图片和宣传视频原文件 | 体积较大，v0.1 的线下收银流程不依赖这些文件 | 如需展示，仅保存文件地址而非文件本体 |
| 供应商内部成本、人员档案和其他客户信息 | 不属于小卖部可管理的数据，且可能涉及商业秘密 | 只保存供货协作所需的联系方式 |
| 复杂促销规则和优惠券活动 | 会明显增加规则和表结构复杂度，不是本阶段最低可运行原型的必需功能 | v0.1 只保留订单折扣金额，后续单独扩展促销模块 |
| 多门店调拨和跨店库存 | 当前场景限定为单门店 | 扩展为连锁场景时增加门店和调拨表 |
| 完整退货审批、退款渠道流水 | 第一阶段重点是正常销售与补货闭环，复杂售后不在最小范围内 | v0.1 可通过订单状态和库存变动备注记录简单异常，后续增加退货单 |
| 监控录像和收银现场录音 | 属于安防系统，数据量大且涉及隐私 | 不纳入经营数据库 |

## 4. 数据使用边界

1. 会员只能查询本人资料、积分和订单，不得查看其他会员信息。
2. 店员只能完成收银所需的商品查询、订单处理和会员识别，不能修改商品售价或手工调整积分。
3. 库存管理员负责入库、盘点和库存查询，不查看与工作无关的会员消费明细。
4. 店长负责商品维护、异常处理、审批和经营报表，可查看门店范围内的经营数据。
5. 供应商是外部协作角色，不直接登录门店内部数据库修改数据。
6. 所有样例姓名、电话和交易记录均为教学用虚构数据，不代表真实顾客或员工。

## 5. v0.1 范围结论

本阶段数据库要形成“商品维护 → 顾客购买 → 订单与明细留存 → 库存扣减 → 会员积分更新 → 低库存发现 → 采购补货 → 库存增加”的最小完整闭环。未列入该闭环的信息不在前四周实现，防止项目范围失控。
