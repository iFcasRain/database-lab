# v0.1 → v1.0 迁移与回归说明（第六周）

## 1. 迁移目标

把通过 v0.1 验收的数据库原地升级为第 7—9 周 Web 应用可用的 v1.0 结构，同时保证：

1. 已有 12 张表的结构、约束和样例数据**一个字段都不改**；
2. 迁移前后的关键业务查询结果完全一致；
3. 迁移脚本可重复执行，重复执行不会重复插入数据；
4. 迁移失败时能够回到 v0.1（不删除数据库，只回退新增对象）。

## 3. 执行顺序与前提

### 3.1 前提

1. 已按 README 依次执行 `00_create_database.sql` 到 `04_crud.sql`；
2. 已执行 `query.sql`、`view.sql`、`constraint.sql`、`role.sql`、`v01_acceptance.sql`，且 `v01_acceptance.sql` 显示“v0.1 验收通过”；
3. 正式样例数据未被测试污染（商品 3、订单 3、明细 5）。

`migration.sql` 开头会检查 `product`、`inventory`、`member`、`employee`、`sales_order`、`sales_order_item`、`inventory_transaction` 是否存在，缺失时直接 `THROW` 终止，避免在半成品库上继续执行。


## 4. 迁移脚本做了什么

`migration.sql` 分为 8 个步骤，每一步都有 `PRINT` 输出，便于在 SSMS 中核对：

| 步骤 | 内容 | 输出 |
|---:|---|---|
| 1 | 迁移前基线快照 | 订单金额、商品销量、库存三组关键查询 |
| 2 | 既有表结构结论 | 每张表的字段数与“保持 v0.1”判定 |
| 3 | 创建 `app_user` | 表已创建 / 已存在跳过 |
| 4 | 创建 3 个应用视图 | 无输出，失败会报错 |
| 5 | 补充 7 个索引 | 无输出，已存在则跳过 |
| 6 | 创建 2 个角色、5 个应用账号、授权 | 角色与账号绑定结果；IMPERSONATE 授权结果 |
| 7 | 写入 5 个演示账号 | 无输出，已存在则跳过 |
| 8 | 迁移结果核对 | 表 13、视图 3、角色 5、账号 5、账号清单 |

### 4.1 数据冲突处理

- **账号重复**：每个 `INSERT` 都带 `NOT EXISTS (SELECT 1 FROM dbo.app_user WHERE username = ...)`，重复执行不会产生重复账号；
- **对象已存在**：表、索引、角色、账号都用 `IF ... IS NULL` 或 `IF NOT EXISTS` 判断；
- **员工/会员编号变化**：演示账号通过 `employee_no = 'E001'`、`member_no = 'M001'` 查找主码，而不是硬编码 301/201，避免 IDENTITY 起点改变后关联错误。

### 4.2 失败恢复

迁移只新增对象，不修改既有数据，因此回退方式很直接：

```sql
-- 回退到 v0.1（保留 12 张表与样例数据）
DROP USER IF EXISTS app_auth, app_customer, app_cashier, app_inventory, app_manager;
DROP ROLE IF EXISTS auth_lookup_role, customer_app_role;
DROP VIEW IF EXISTS dbo.vw_product_catalog, dbo.vw_active_cashier, dbo.vw_order_summary;
DROP TABLE IF EXISTS dbo.app_user;
-- 索引可按需删除：DROP INDEX IX_sales_order_member ON dbo.sales_order;（其余同理）
```

若需要彻底重来，删除数据库后按第 3.2 节顺序重新执行即可。**不要**用“删库重建”代替迁移，那会丢失已有数据。

### 6.1 为什么表数量从 12 变成 13 是合理的

`app_user` 是一个独立实体（见 ER 图的 R17、R18），承载登录名、口令摘要与角色，不能用 `member` 或 `employee` 的字段代替。它不改变任何既有表的行数，也不参与订单金额、库存和积分的计算，因此不影响业务结果。

### 6.2 为什么视图从 4 变成 7

新增的 3 个视图都只读，目的是让权限受限的角色（例如顾客）在不获得 `employee` 基表授权的前提下也能看到经办店员姓名。视图由 `dbo` 拥有，底层表与视图的所有者相同，因此走所有权链（ownership chaining），不需要额外授予基表权限。

## 7. 可重复执行说明

| 脚本 | 可重复执行 | 说明 |
|---|---|---|
| `migration.sql` | 是 | 全部使用“不存在才创建”，账号插入带 `NOT EXISTS` |
| `regression.sql` | 是 | 只读检查，权限用例在事务中回滚 |
| `v01_acceptance.sql` | 是（但结论会变） | 它检查的是 **v0.1 状态**（业务表 12 张）。迁移后重跑会因表数为 13 而显示 FAIL，这属于预期结果，迁移之后请改用 `regression.sql` 验收 |
| `01_create_tables.sql` | 否 | 检测到目标表存在即 `THROW`，保护已有数据 |
| `03_insert_sample_data.sql` | 否 | 检测到样例行即 `THROW`，避免重复插入 |

`migration.sql` 再次运行所需的初始状态就是“已完成 v0.1 验收、且已运行过一次 migration 或尚未运行均可”。
