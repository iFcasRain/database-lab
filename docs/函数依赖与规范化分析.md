# 函数依赖与规范化分析（第六周）

## 1. 分析对象与基线

分析对象是 v0.1 的 12 张表，以及第六周迁移新增的 `app_user`（共 13 张）。基线数据是第三周装载的样例数据（3 个分类、3 个商品、3 张订单、5 条明细、3 位会员、3 名员工、3 家供应商、3 张采购单），迁移前先由 `migration.sql` 输出关键查询结果作为对照基准。

记号约定：

- `X → Y`：X 函数决定 Y；
- 主属性：包含在任一候选码中的属性；非主属性：其余属性；
- 1NF 要求属性不可再分，2NF 要求非主属性完全依赖于每个候选码，3NF 要求不存在非主属性对候选码的传递依赖，BCNF 要求每个非平凡函数依赖的决定因素都是超码。

## 2. 逐表函数依赖

### 2.1 category（商品分类）

- 候选码：`category_id`、`category_code`、`category_name`
- 主要函数依赖：
  - `category_id → category_code, category_name, status, created_at`
  - `category_code → category_id, category_name, status, created_at`
  - `category_name → category_id, category_code, status, created_at`
- 判断：三个候选码都是单属性，非主属性完全依赖候选码，不存在部分依赖；`status`、`created_at` 只由候选码决定，不存在传递依赖。
- 结论：**BCNF**。

### 2.2 product（商品）

- 候选码：`product_id`、`product_code`、`barcode`
- 主要函数依赖：
  - `product_id → product_code, barcode, product_name, category_id, unit, selling_price, status, created_at`
  - `product_code → …`（同上）
  - `barcode → …`（同上）
- 判断：商品表**没有保存** `category_name`，因此不存在 `product_id → category_id → category_name` 的传递依赖。价格是商品自身属性，不是由分类决定的。
- 结论：**BCNF**。
- 说明：如果按“方便查询”的直觉把分类名称冗余到商品表，就会产生传递依赖（违反 3NF），并在修改分类名称时出现更新异常。当前设计刻意避免了这一点。

### 2.3 inventory（当前库存）

- 候选码：`product_id`（同时是主码和外码）
- 主要函数依赖：`product_id → quantity, reorder_level, updated_at`
- 判断：单属性主码，非主属性完全依赖，无传递依赖。
- 结论：**BCNF**。

### 2.4 member（会员）

- 候选码：`member_id`、`member_no`、`phone`
- 主要函数依赖：
  - `member_id → member_no, member_name, phone, points_balance, registered_at, status, remark`
  - `member_no → …`、`phone → …`（同上）
- 判断：`points_balance` 是会员的当前状态，虽然可由积分流水累加得到（见第 6 节的反规范化取舍），但在本表内部不存在传递依赖。
- 结论：**BCNF**。

### 2.5 employee（员工）

- 候选码：`employee_id`、`employee_no`、`phone`
- 主要函数依赖：`employee_id → employee_no, employee_name, phone, job_type, hire_date, status, created_at`
- 判断：`job_type` 只由员工自身决定，没有“岗位编号 → 岗位名称”的传递依赖（岗位是枚举域而不是独立实体，这是有意的简化）。
- 结论：**BCNF**。

### 2.6 supplier（供应商）

- 候选码：`supplier_id`、`supplier_code`
- 主要函数依赖：`supplier_id → supplier_code, supplier_name, contact_name, phone, address, status, created_at`
- 判断：供应商名称可能重名，因此不作为候选码，但也**没有**被其他属性决定，不存在传递依赖。
- 结论：**BCNF**。

### 2.7 sales_order（销售订单）

- 候选码：`order_id`、`order_no`
- 主要函数依赖：
  - `order_id → order_no, member_id, cashier_id, order_time, order_status, payment_method, original_amount, discount_amount, paid_amount`
  - `order_no → …`（同上）
- 判断：订单级属性只由订单本身决定。`member_id` 只作为外码保存，会员姓名不在本表冗余，因此没有 `order_id → member_id → member_name` 的传递依赖。
- 结论：**BCNF**（`paid_amount` 的派生问题见第 6 节）。

### 2.8 sales_order_item（销售订单明细）

- 候选码：`order_item_id`；复合候选码 (`order_id`, `product_id`)
- 主要函数依赖：
  - `order_item_id → order_id, product_id, quantity, unit_price`
  - (`order_id`, `product_id`) → `quantity, unit_price`
- 判断：
  - 1NF：每列都是原子值，一张订单的多个商品拆成多行，没有重复组。
  - 2NF：`quantity` 与 `unit_price` 依赖的是“订单 + 商品”这一组合，而不是单独的 `order_id` 或 `product_id`，不存在部分依赖。
  - 3NF / BCNF：两个决定因素 `order_item_id` 与 (`order_id`, `product_id`) 都是候选码，因此是 **BCNF**。
- 说明：明细中保存的是**成交单价**，它由“本单本次交易”决定，不能由商品当前售价决定。这正是把 `unit_price` 放在明细而不是让订单明细去读 `product.selling_price` 的原因。

### 2.9 points_transaction（积分流水）

- 候选码：`points_transaction_id`、`transaction_no`
- 主要函数依赖：`points_transaction_id → transaction_no, member_id, order_id, change_type, points_change, balance_after, occurred_at, remark`
- 判断：`order_id` 不是候选码（一笔订单可以产生抵扣与获得两条流水），因此不能靠 `order_id` 定位一行；`balance_after` 记录的是本次变动后的快照，属于历史事实，不由其他列推导。
- 结论：**BCNF**。

### 2.10 purchase_order（采购单）

- 候选码：`purchase_order_id`、`purchase_order_no`
- 主要函数依赖：`purchase_order_id → purchase_order_no, supplier_id, created_by, approved_by, order_date, order_status, total_amount, approved_at`
- 判断：`supplier_id`、`created_by` 均为外码，供应商名称与员工姓名不冗余，无传递依赖。
- 结论：**BCNF**（`total_amount` 的派生问题见第 6 节）。

### 2.11 purchase_order_item（采购明细）

- 候选码：`purchase_order_item_id`；复合候选码 (`purchase_order_id`, `product_id`)
- 判断：与销售明细同理，`ordered_quantity`、`received_quantity`、`purchase_unit_price` 依赖完整的“采购单 + 商品”组合。
- 结论：**BCNF**。

### 2.12 inventory_transaction（库存流水）

- 候选码：`inventory_transaction_id`、`transaction_no`
- 主要函数依赖：`inventory_transaction_id → transaction_no, product_id, transaction_type, quantity_change, sales_order_id, purchase_order_id, operator_id, occurred_at, remark`
- 判断：`sales_order_id` 与 `purchase_order_id` 都可空且不唯一，属于历史事实记录。
- 结论：**BCNF**。

### 2.13 app_user（应用账号，第六周新增）

- 候选码：`user_id`、`username`
- 主要函数依赖：
  - `user_id → username, password_hash, display_name, role, employee_id, member_id, status, created_at, last_login_at`
  - `username → …`（同上）
- 判断：
  - 身份映射由 `CK_app_user_identity` 保证“员工外码与会员外码恰好一个非空”，不会出现两个都填的异常组合；
  - `display_name` 与 `employee_name` / `member_name` 存在**有意为之**的冗余，见第 6 节。
- 结论：**BCNF**。

## 3. 更新异常分析

对每张表分别检查插入、修改、删除异常。判断标准是：一次业务操作是否必须同时修改多处，或者删除一条记录是否会连带丢失不相干的信息。

| 表 | 插入异常 | 修改异常 | 删除异常 | 结论 |
|---|---|---|---|---|
| category | 可以先建分类、后建商品（分类允许没有商品） | 改分类名只需改一行 | 删分类前必须先处理商品，符合业务 | 无异常 |
| product | 新增商品必须同时建库存（业务要求，不是结构缺陷） | 调价只改一行，历史订单的成交单价不受影响 | 删除商品会因外码被阻止，符合“商品不可随意删除”的业务 | 无异常 |
| inventory | 与商品 1:1，插入由新增商品触发 | 盘点只改数量并写流水 | 删除库存记录会使商品失去库存，业务上不允许 | 无异常 |
| member | 可以先建会员、后产生订单 | 改姓名只改一行；订单引用 `member_id` 不受影响 | 删除会员可能导致订单失去归属，实际按“停用”处理 | 无异常 |
| employee | 可以先建员工、后经办订单 | 改岗位不影响历史订单的经办人外码 | 删除员工被外码阻止 | 无异常 |
| supplier | 可以先建供应商、后建采购单 | 改联系人不影响采购单 | 删除供应商被外码阻止 | 无异常 |
| sales_order | 订单可以先创建为 `PENDING` | 订单金额由明细一次算出，写入后不允许改明细 | 取消订单是改状态而不是删记录，保留审计 | 无异常（派生字段见第 6 节） |
| sales_order_item | 明细必须跟随订单写入 | 明细写入后视为交易事实，不再修改 | 删除订单时一并删除明细，属于整体操作 | 无异常 |
| points_transaction | 流水必须跟随积分变动写入 | 流水是历史事实，不允许修改 | 删除流水会破坏积分链 | 无异常 |
| purchase_order | 可以先建草稿采购单 | 审批后写审批人与时间 | 取消采购单是改状态 | 无异常 |
| purchase_order_item | 明细必须跟随采购单 | 实收数量在收货时更新 | 与采购单整体删除 | 无异常 |
| inventory_transaction | 流水跟随库存变动写入 | 流水不允许修改 | 不允许删除，保证可追溯 | 无异常 |
| app_user | 账号必须同时绑定员工或会员之一 | 改角色只改一行，历史订单仍指向员工/会员外码 | 停用账号而不删除，保留审计 | 无异常 |

### 3.1 用独立演示关系说明“如果不拆分会怎样”

为了说明拆分的必要性，构造一个**假想**的平表（不进入数据库）：

`ORDER_FLAT(order_no, order_time, member_name, cashier_name, product_name, unit_price, quantity, paid_amount)`

| order_no | member_name | cashier_name | product_name | unit_price | quantity | paid_amount |
|---|---|---|---|---|---|---|
| SO001 | 张晓雨 | 刘收银 | 饮用天然水 | 2.00 | 2 | 7.00 |
| SO001 | 张晓雨 | 刘收银 | 纯牛奶 | 3.50 | 1 | 7.00 |

这张表的问题：

1. **插入异常**：想登记一个新商品但还没有订单时，无处可插（主码包含订单号）。
2. **修改异常**：把“刘收银”改名为“刘收银（收银组长）”，必须同时改该收银员的所有明细行；漏改就出现同名不同字的矛盾数据。
3. **删除异常**：删除订单 SO001 的两行，会同时丢掉“饮用天然水”“纯牛奶”这些商品信息。

分解为 `sales_order`（订单级）、`sales_order_item`（明细级）、`product`、`employee`、`member` 五张表后，三类异常都不再出现。这正是 v0.1 已经采用的结构。

## 4. 范式结论汇总

| 表 | 1NF | 2NF | 3NF | BCNF | 说明 |
|---|---|---|---|---|---|
| category | 是 | 是 | 是 | 是 | 三个单属性候选码 |
| product | 是 | 是 | 是 | 是 | 未冗余分类名 |
| inventory | 是 | 是 | 是 | 是 | 主码即外码 |
| member | 是 | 是 | 是 | 是 | 余额为当前状态 |
| employee | 是 | 是 | 是 | 是 | 岗位为枚举域 |
| supplier | 是 | 是 | 是 | 是 | 名称不唯一 |
| sales_order | 是 | 是 | 是 | 是 | 金额为派生字段，见第 6 节 |
| sales_order_item | 是 | 是 | 是 | 是 | 复合候选码，无部分依赖 |
| points_transaction | 是 | 是 | 是 | 是 | 余额为历史快照 |
| purchase_order | 是 | 是 | 是 | 是 | 金额为派生字段，见第 6 节 |
| purchase_order_item | 是 | 是 | 是 | 是 | 复合候选码 |
| inventory_transaction | 是 | 是 | 是 | 是 | 来源单据可空 |
| app_user | 是 | 是 | 是 | 是 | 显示名冗余，见第 6 节 |

**结论：13 张表均满足 3NF 与 BCNF，不需要进一步分解。**

## 5. 无损连接与依赖保持

由于最终方案没有拆分任何表，无损连接与依赖保持是**平凡成立**的。为了说明“即使拆分也不会丢信息”，对一次假想分解做论证：

设 `R(A, B, C)` 满足 `A → B`、`A → C`，拆分为 `R1(A, B)` 与 `R2(A, C)`。

- 无损连接：两表的公共属性是 `A`，且 `A → B` 与 `A → C` 都成立，`A` 是 `R1` 与 `R2` 的候选码，因此连接后不会产生伪元组，分解是无损的。
- 依赖保持：`A → B` 在 `R1` 中、`A → C` 在 `R2` 中，两条函数依赖都被保留。

反例：如果把 `sales_order` 拆成 `(order_id, order_no, member_id)` 与 `(order_no, cashier_id, paid_amount)`，公共属性 `order_no` 是第二张表的主码，仍然无损；但如果拆成 `(order_id, order_no)` 与 `(member_id, cashier_id)`，公共属性为空，连接后会变成笛卡尔积，属于**有损分解**。这也是第 3 周建表时坚持“外码指向主表主码、不拆开单据级属性”的原因。

## 6. 反规范化取舍

v0.1 中有五类刻意保留的冗余，都属于“用少量冗余换取读取效率或历史可追溯性”，并且都有相应的一致性保证：

| 冗余字段 | 可由什么推导 | 为什么保留 | 如何防止不一致 |
|---|---|---|---|
| `sales_order.original_amount` | `SUM(quantity × unit_price)` | 列表页与对账不必每次聚合明细 | 下单事务中一次写入；`regression.sql` 检查“原价 = 明细合计” |
| `sales_order.paid_amount`、`discount_amount` | `original_amount` 与积分规则 | 同上，并支持“待支付实付为 0”的状态语义 | `CK_sales_order_amounts` 强制 `实付 = 原价 − 优惠` |
| `member.points_balance` | 积分流水累加 | 结算时需快速读取余额 | 与流水同事务更新；`regression.sql` 校验余额 = 最后一条流水 |
| `inventory.quantity` | 库存流水累加 | 库存页与下单校验需快速读取 | 与流水同事务更新；`CK_inventory_quantity` 禁止负数 |
| `app_user.display_name` | `employee.employee_name` 或 `member.member_name` | 登录后立即显示，避免每次联查两张表；也允许账号显示名与真实姓名不同 | 迁移时按姓名写入；显示名只用于界面，不参与业务判断 |

### 6.1 为什么这些冗余可以被接受

1. 冗余字段都是**只由本事务写入、不接受随意修改**的字段，不存在“两个入口分别改”的情况；
2. 每个冗余字段都配有至少一条回归检查（第 6 周 `regression.sql` 的金额、积分、库存三项）；
3. 业务的读取频率远高于写入频率：每次下单要读库存与价格，每次展示要读金额，而写入只在结算时发生一次。

## 7. 结论

1. v0.1 的 12 张表在 1NF、2NF、3NF、BCNF 上均无问题，不需要拆分或合并；原先担心的“类别名称重复”“历史价格被覆盖”等问题在当前结构下并不存在；
2. 真正需要补充的是与 Web 应用相关的 `app_user` 实体、查询索引和受权限控制的视图，这些都以“新增”的方式在 `migration.sql` 中完成；
3. 保留的冗余字段有明确理由与一致性检查，属于可控的反规范化，而不是设计缺陷；
4. 迁移前后用固定样例数据和关键查询比对，业务含义不变，见[迁移与回归说明](迁移与回归说明.md)。
